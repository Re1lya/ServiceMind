# ServiceMind MVP 方案

## 1. MVP 核心目标

MVP 的目标不是一次性做完整客服平台，而是在最短周期内验证以下三件事：

1. 用户是否愿意使用 AI 客服完成高频咨询
2. 系统是否能稳定处理 FAQ 与订单、物流类核心问题
3. Agent + RAG + 工具调用的组合链路是否具备业务可行性

## 2. MVP 核心功能范围

### P0：必须具备

- 用户聊天工作台
- 多轮对话基础能力
- FAQ/RAG 知识问答
- 订单查询工具
- 物流查询工具
- 会话日志记录
- 异常兜底与人工转接提示

### P1：强烈建议

- 投诉登记或工单创建
- 简单意图识别与场景路由
- 检索日志与工具调用日志
- 管理端知识库导入功能

### P2：可延后

- LoRA 微调模型
- 混合检索高级优化
- 多租户与权限体系
- 运营看板与自动评测平台

## 3. MVP 功能优先级排序

| 优先级 | 模块 | 原因 |
|---|---|---|
| P0 | 对话主链路 | 没有聊天链路，系统无法演示和验证 |
| P0 | RAG 知识问答 | 解决大部分标准化客服问题 |
| P0 | 订单查询 | 最常见的客服诉求之一 |
| P0 | 物流查询 | 与订单场景强相关，业务价值高 |
| P0 | 日志与兜底 | 上线验证必须具备可追踪性 |
| P1 | 投诉/工单 | 完善售后闭环 |
| P1 | 意图识别 | 提升路由准确率与可维护性 |
| P2 | 微调与评测 | 更偏效果优化，而非首版上线门槛 |

## 4. MVP 建议范围

### 用户侧能力

- 输入自然语言问题
- 查看流式回答
- 查询订单与物流
- 获得知识型问题答案
- 在无法处理时收到人工转接提示

### 后台侧能力

- 上传 FAQ/客服知识文档
- 重建知识索引
- 查看基础会话日志

## 5. 开发周期预估

假设团队配置为 `1 名前端 + 1 名后端/AI 工程师 + 1 名兼产品测试`，推荐周期如下：

| 周期 | 交付内容 |
|---|---|
| 第 1 周 | 需求梳理、技术选型、数据表设计、前后端项目初始化 |
| 第 2 周 | 聊天主链路打通，完成基础前后端通信与流式输出 |
| 第 3 周 | RAG 知识库导入、切分、检索、回答生成 |
| 第 4 周 | 接入订单查询与物流查询工具 |
| 第 5 周 | 补充日志、兜底、错误处理、体验优化 |
| 第 6 周 | 联调测试、示例数据构造、验收演示 |

### 更激进的个人项目节奏

- `2~3 周` 可完成简化版 MVP
- 前提是只做单租户、少量接口、简化后台和本地部署

## 6. MVP 落地验证标准

### 功能验证

- 用户可以完成至少 3 类问题交互：
  - FAQ 咨询
  - 订单状态查询
  - 物流轨迹查询

### 效果验证

- FAQ 类问题回答可用率达到 `80%+`
- 订单与物流类工具调用成功率达到 `95%+`
- 平均响应时间控制在 `3~8 秒`
- 固定检索评估集可重复运行，并记录 Hit@1、Recall@3、Recall@5、MRR
- 知识问答回答必须返回来源片段，阶段性统计回答可依据率

### 工程验证

- 关键日志可追踪
- 服务可本地一键启动
- 核心接口具备基本异常处理
- 知识库支持重复导入与重建
- 知识问答结果能返回并展示命中来源片段
- 离线知识库构建脚本能批量处理 `data/raw`，并输出文档数、chunk 数、失败数和耗时
- 阶段验证结果沉淀到 [evaluation-report.md](/D:/pythoncode/ServiceMind/docs/evaluation-report.md)

### 业务验证

- 能覆盖至少 `60%` 的高频客服问题
- 演示中能体现减少人工重复劳动的价值

## 7. 核心风险点

### 风险 1：知识库效果不稳定

- 表现：问答命中率低，回答泛化严重
- 应对：优先建设高质量 FAQ 数据，增加混合检索与 rerank

### 风险 2：工具调用链路不稳定

- 表现：订单或物流接口超时、返回异常
- 应对：增加超时控制、重试机制和失败兜底文案

### 风险 3：模型幻觉影响业务可信度

- 表现：模型编造订单状态、售后政策
- 应对：强约束 prompt，业务字段必须来自工具返回或检索结果

### 风险 4：上下文过长导致成本和延迟升高

- 表现：长对话时响应慢、费用高
- 应对：做摘要记忆、窗口裁剪和结构化状态存储

### 风险 5：MVP 范围失控

- 表现：想同时做微调、评测、运营后台，导致延期
- 应对：严格按 P0/P1/P2 控制范围，先验证主价值链路

## 8. 建议的 MVP 技术取舍

- 前端优先做单页面工作台，不先做复杂后台
- 后端优先做单体服务，不先拆微服务
- 当前先使用本地 `FAISS` 验证向量召回闭环，并保留轻量词法检索作为回退；后续按知识库管理和规模需求评估 `ChromaDB`
- 工具调用先做 2 个高频工具，避免接口铺太大
- 微调不作为 MVP 上线前置条件，优先使用现成 API 模型

## 9. 验收输出建议

MVP 阶段建议至少形成以下可交付物：

- 可运行演示系统
- 项目 README
- 架构流程图
- 核心接口文档
- 典型测试用例
- 离线知识库构建脚本与处理报告
- 固定评估问题集
- 阶段验证与召回结果文档
- 演示脚本或录屏
